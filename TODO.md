# TODO: использование генератора PDF из PHP-приложения

## Разделение ответственности

- **PHP**: форма входа, коннект к БД, изоляция клиентских данных,
  форма с полями для генерации PDF.
- **Node (этот проект)**: только генерация PDF, без доступа к БД
  и без знания чужих клиентов.

## Текущий API генератора (важно)

- `index.js` экспортирует `init(settings)` + `quote/invoice/packing/return/receipt/refund(order, payment)`
  (асинхронные, возвращают `Promise<Buffer>`).
- `init()` кладёт `company/logo/язык/валюту/шрифты` в **глобальный `config`**.
  Долгоживущий Node-процесс с параллельными запросами разных клиентов
  даст гонку (один `init` перезапишет другой).
- Вход: JSON-объекты (`types/main.d.ts`: `CompanyInfo`, `Order`, `Payment` + `logo: Buffer`).
- Выход: бинарный PDF. Логотип/QR везём как base64 или файлами.

## Вариант A (рекомендуется): Node HTTP-микросервис на localhost

- PHP делает `curl POST /invoice` с JSON → получает `application/pdf`.
- Плюсы: тёплый процесс, версионирование (`/v1/...`), таймауты/ретраи/метрики.
- Минусы: нужен файл-адаптер (`server.js`), токен между PHP и Node,
  супервизор (systemd/docker).
- Слушать только `127.0.0.1`, лимит тела (5–10 МБ), таймаут PHP-клиента 10–30 с.

## Вариант B (простой старт): CLI через `exec`

- PHP кладёт JSON во временный файл, `node render.js` печатает PDF в stdout/файл,
  PHP читает, отдаёт пользователю, временные файлы удаляются.
- Плюсы: максимальная изоляция (свежий процесс на запрос), ноль сети.
- Минусы: старт Node ~100–200 мс на запрос, аккуратная работа
  с `escapeshellarg`, временными файлами и таймаутами.
- Для десятков PDF в минуту — нормально; для сотен в секунду — вариант A.

## Контракт

- `POST /v1/{quote,invoice,packing,return,receipt,refund}`
  (или один `/v1/render {docType, ...}`).
- Request JSON: `{ company, order, payment?, options?: { language, locale, currency, page } }`.
- Response: `200 application/pdf` (бинарь) + `X-Request-Id`.
- Ошибки: `4xx` (валидация) / `5xx` (рендер упал), тело `{ error, requestId }`.
- Авторизация сервиса: общий секрет в header (`X-Render-Token`).

## Изоляция клиентских данных (сторона PHP)

- Аутентификация, ACL и БД — только в PHP; Node в БД не ходит.
- PHP собирает для Node минимальный JSON только текущего пользователя.
- Вариант B: процесс умер — данные умерли; чистить tmp-файлы сразу после отдачи.
- Вариант A: не логировать тела с ПДн, `requestId` без ПДн,
  `init+generate` выполнять атомарно (очередь/мьютекс), чтобы глобальный
  `config` не пересекался между клиентами.

## Хранение данных MySQL (Docker)

- Данные клиентов лежат в именованном томе `invoice-pdfkit_mysql-data`
  (`mysql-data` в `docker-compose.yml`); `docker build` / `up` том не трогают.
- Потеря возможна только при удалении тома: `docker compose down -v`,
  `docker volume prune` / `docker system prune --volumes`, либо кнопка **Down**
  в PhpStorm (по докам IDE удаляет и тома; Stop/Restart безопасны).
- [ ] Защитить том: объявить `mysql-data` внешним (`external: true`,
  `name: invoice-pdfkit_mysql-data`) или перейти на bind mount
  `./mysql-data:/var/lib/mysql` (каталог уже в `.gitignore`).
- [ ] Проверить, что том не создаётся заново при смене имени проекта/каталога
